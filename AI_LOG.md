# AI_LOG

Running log of overrides, flags, and judgment calls. Written as they happened, not summarised afterward.

## Research

- **[AI flag]** The `/api/docs` page is a JS single-page app and returns no usable content to a fetcher. Found the real OpenAPI spec at `data.jambase.com/openapi.json` (v3.1.0) and worked from that instead of the rendered docs.
- **[AI flag]** `GET /events` has **no city-name parameter**, and it rejects unknown params with a hard `400` rather than ignoring them (`?geoCityName=Austin` → `Unknown Query Parameter`). Free-text location therefore *requires* a two-call flow: resolve the name via `/geographies/cities`, then query events by `geoCityId`. This is the single fact that shaped the provider's design.
- **[AI flag]** Profiled a real 100-event sample before choosing what to surface. Three spec-vs-reality mismatches found: prices arrive as **strings** (`"15.00"`) though the spec declares `type: number`; absent `previousStartDate`/`doorTime` are **empty strings**, not null; and `startDate` is a datetime while `endDate` is sometimes date-only. These are the concrete justification for normalising in the adapter.
- **[AI flag]** No `X-RateLimit-*` headers on any response, so there is no documented budget to back off against. Cache is the only quota defence available.
- **[AI flag]** Pricing is **not** reliably available — only 67 of 278 offers (24%) carried a price. Flagged that the brief's assumption of pricing data was optimistic, and that this had to ship as a best-effort signal with visible absence rather than a claimed feature.

## Product design

- **[USER OVERRIDE]** I proposed making **resale market depth** (count of distinct secondary marketplaces per event) a headline UI signal, reasoning from the employer being a ticket-resale trading desk — 181 of 278 offers in my sample were secondary listings, which is a genuine liquidity proxy. Dhruv rejected it: the product requirement is a *normal user deciding which event to attend*, not the employer's internal trading workflow, and the UI should be optimised for that user. Replaced with headliner + genre artist context. This was optimising for who was reading the case study rather than who was using the product, and the correction was right.
- **[USER OVERRIDE]** I offered `lat,lng` radius input as a second location mode to show the adapter handling multiple upstream strategies. Cut as scope creep — one location input mode only.

## Build

- **[USER OVERRIDE]** I planned a server-rendered Jinja2 UI, justifying it as avoiding drift between the HTML and JSON paths. Dhruv corrected both the choice and my reasoning: a static page + `fetch` makes the JSON API the *only* data path, exercised the way any external client would use it — and my stated justification was weak, since both routes already awaited the same provider call. Dropped the Jinja dependency.
- **[USER OVERRIDE]** I planned `start_time_known: bool` alongside a datetime. Replaced with `event_date: date` + `event_time: time | None`, which represents what JamBase actually knows instead of encoding it in a side flag.
- **[USER DIRECTION]** Never aggregate prices across currencies. A range is computed only when all priced offers for an event agree on currency; conflicting currencies expose pricing as unavailable rather than emitting something like `$15–€80`.
- **[Judgment call]** I started writing `fetch_events` to return a wrapper object carrying the *resolved* location, so the UI could show that "Austin" resolved to Austin, TX rather than Austintown, OH. That contradicts the specified signature `fetch_events(location, days) -> list[Event]`, which is explicitly part of what's being graded, so I reverted to the exact signature. The disambiguation need is still met: every `Event` carries its venue's city and region, so the resolved place is visible in the results themselves without widening the contract.
- **[Judgment call]** Checked whether JamBase uses `T00:00:00` as a "time unknown" sentinel before writing the date parser. It does not — across 100 real events, 99 carried a genuine showtime and 1 was date-only, with zero midnights. So date-only means unknown and midnight is treated as a real showtime. Guessing either way without checking would have silently mangled late shows.
- **[Judgment call]** Found a fourth upstream inconsistency while writing the adapter: `addressRegion` is an **object** on `/events` but a **plain string** on `/geographies/cities`. Handled by one `_region_code` helper rather than two code paths.
- **[Judgment call]** A region hint that matches no city (e.g. "Austin, ZZ") returns "not found" rather than falling back to the best city in the wrong state. Silently returning Austin, TX events for a query the user scoped elsewhere is worse than an honest miss.
- **[Judgment call]** A single malformed event record is skipped and logged, not raised. One bad row upstream should not blank an entire search.
- **[Judgment call]** An unrecognised `eventStatus` degrades to `UNKNOWN`, not to `SCHEDULED`. Defaulting to "scheduled" would assert a show is on when the provider is telling us something we don't understand.
- **[Judgment call]** Exact version pins broke the install on Python 3.14 (no `pydantic-core` wheel; it tried to compile from source). Switched `requirements.txt` to lower bounds so the reviewer's machine isn't a lottery, and noted in the file that a production service would pin exactly via a lockfile.
- **[AI flag]** `/health` deliberately does **not** call JamBase. Verified live: with the upstream blackholed, `/health` still returns 200 while `/events` returns a clean 504. A health check that depends on a third party converts their outage into our restart loop, and would burn trial quota on every probe.
- **[Limitation — later resolved]** At first I could not visually verify the UI: the Chrome extension wasn't connected. Recorded as an open limitation rather than glossed over. Resolved later by rendering with headless Chrome directly (see below).
- **[Judgment call]** Built the test fixture from a **real captured JamBase response** rather than hand-written JSON, deliberately slicing it to include the cases that break naive adapters: a cancelled show, a rescheduled show carrying a real `previousStartDate`, a date-only festival, an event with zero offers, and string-typed prices. Hand-written fixtures would have encoded my assumptions about the API instead of testing them.
- **[Judgment call]** Added a test asserting an upstream error body (`"db-07.internal"`) never appears in the exception surfaced to a caller. Leaking upstream internals through an error path is the kind of thing that passes review and then shows up in a bug bounty report.
- **[Judgment call]** Ran a claim-vs-code audit before finishing: grepped every factual assertion in README and WRITEUP against the source (routes never import the concrete provider; no `innerHTML`; no retry/backoff code; no linter config; 24 tests; `perPage` 60; no pagination follow). All held. One inaccuracy found and fixed — the README's example response had a trimmed `ticket_url`; replaced with the value the API actually returns.

## Real-browser verification (Claude in Chrome connected)

- **[AI flag — defect headless hid]** Rendering in the real browser exposed a locale bug that headless Chrome had masked behind its own default. This machine reports `navigator.language` = **en-US** but `Intl.DateTimeFormat().resolvedOptions().locale` = **en-GB**, because the macOS regional format overrides the browser language. Passing `undefined` to `toLocaleTimeString`/`Intl.NumberFormat` follows the *system region*, so every card rendered "19:00" and "US$15" instead of "7:00 PM" and "$15". I had previously assumed this was a headless artifact that would resolve on a normal machine — that assumption was wrong, and only a real browser disproved it.
- **[USER DECISION]** Asked Dhruv which locale should win rather than deciding unilaterally, having already been corrected once for making a product call on his behalf. He chose formatting from `navigator.language`. Applied and verified live.
- **[Verified live in-browser]** Error state: "Nowhereville12345" renders the API's message in a styled box with results cleared — no blank page, no console errors. Ambiguity: "Austin" with no state resolves to Austin, TX (every venue line reads "Austin, TX"), confirming `_pick_city` prefers the exact name match over the busier fuzzy one. Cancelled card: struck-through title, red badge, no price, no ticket link.

## Backend quality pass

- **[USER REVERSAL — architectural]** Dhruv overrode his own earlier requirement that `fetch_events` return `list[Event]`, after real output showed the problem: returning 60 events when JamBase reports 268 available presents a truncated slice as a complete answer. The provider Protocol now returns a `SearchResult` envelope carrying `total_available` and `resolved_location`. Worth recording that the reversal came from observing real data, not from a design preference — and that I had raised the constraint as a limitation rather than changing it unilaterally, having already been corrected once for deviating from a specified signature.
- **[Judgment call]** Made `returned_count` a **computed** field derived from `len(events)` rather than a stored one. The requirement was that the two must always agree; deriving it means no caller can construct a `SearchResult` where they disagree, which enforces the invariant instead of merely validating it. Flagged because the spec listed it as a field — trivially reversible if you want it stored.
- **[Judgment call]** A `totalItems` smaller than the page we just received is internally inconsistent, so it is discarded and reported as unknown rather than passed through. Same rule as absent pricing: an absent number is honest, a wrong one is worse than nothing.
- **[Judgment call]** Three distinct UI messages rather than one: "Showing the first N of M" when truncated, a plain count when complete (no truncation implied), and an explicit "the provider did not report a total, so there may be more" when the total is unknown. The third case exists because absent metadata is its own state, not a silent fallback to "complete".
- **[Judgment call]** Constructed the route tests with `TestClient(app)` *without* the context manager, so the lifespan never runs. That means no real `httpx` client is built and **no API key is needed to run the suite** — the tests work on a clean checkout with no `.env`, which they would not if the lifespan constructed `JamBaseProvider`.
- **[AI flag — my own test was wrong]** My first substitutability test grepped `app/routes.py` for the string "jambase" and failed, because the module's own docstring explains that it deliberately doesn't import JamBase. Rewrote it to parse the AST and assert on the actual import graph. A test that fails on a docstring would also have *passed* for the wrong reason later.
- **[Judgment call — flagged before implementing]** "Transport failure" needed splitting. `ConnectError`, `ConnectTimeout`, `PoolTimeout`, `ReadError`, `WriteError` and `RemoteProtocolError` are retried — they fail fast and often succeed second time. `ReadTimeout`/`WriteTimeout` are **not**: the request already consumed its entire time budget, so retrying would double an interactive user's wait (up to 20s at our 10s read timeout) to buy one more chance at an upstream that is already slow. Retrying every `httpx.TimeoutException` uniformly would have been the obvious reading of "transport failures" and the wrong one.
- **[Judgment call]** An unparseable `Retry-After` (including the legal HTTP-date form, which we do not parse) fails cleanly rather than falling back to our own short delay. Falling back would mean ignoring an explicit instruction from the provider — the wrong direction to err when the provider is telling us to back off.
- **[Judgment call]** Checked the JamBase OpenAPI spec for a documented `perPage` ceiling rather than probing the live API. The spec states it explicitly: `{"type":"integer","default":40,"minimum":1,"maximum":100}`. Raised our request from 60 to the documented 100. This reduces truncation but does not fix completeness — a 30-day Dallas search now returns 100 of 262 — which is exactly why the `SearchResult` disclosure is the actual correctness fix and this is only a mitigation.
- **[Judgment call]** Cache tests use an injected fake monotonic clock rather than real sleeps, so TTL expiry is tested deterministically and the suite still runs in well under a second. The two-TTL design gets a test that states its actual purpose: after an hour, events are refetched but the city lookup is **not** repeated.
